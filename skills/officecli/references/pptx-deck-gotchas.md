# officecli pptx deck-build gotchas (проверено 17.10, дек Khomen Wheels)

Реальные ловушки, не покрытые SKILL.md. Использовать при сборке любого pptx-дека.

## Addressing: шейпы и параграфы
- `add --type paragraph`: parent = **сам шейп** `/slide[N]/shape[@name=X]`, НЕ `...paragraph[1]`. Parent-paragraph батч валит («Text '.' not found»), и атомарный батч откатывается целиком.
- Первое пустое `paragraph[1]` шейпа заполнять через `set` по `.../paragraph[1]` (текст+шрифт+размер+цвет одной пачкой), последующие строки — `add` в шейп.
- Числа в кружках/иконок-оверлеи: **отдельный текст-шейп поверх** (width как у круга, height ~1.2cm, `y = circle.y + (circle.h − label.h)/2`, valign=middle). Инъекция run'а через `--after find:.` легко улетает в соседний шейп — у нас тайтл стал «АгентАГЕНТ …», чинилось find/replace по `paragraph[1]`.

## Тихая грязь (silent pollution)
- `add` с битым пропом (`--prop prop=text=...`, вложенный prop=) может **создать пустой шейп**: id выделен, текста нет, ошибка не показана. После каждого батча — `get /slide[N] --depth 1`, пустые (текст `""`) удалять по `@id`.
- Слайд может «не создаться» при фейле середины цепочки `&&` — дальше все `/slide[N]` смещаются. После любого фейла: `officecli view file outline` и пересчитать слайды.

## find/replace: границы ранов
- Текст, разорванный на несколько ранов, на уровне слайда `/slide[N]` НЕ матчится (0 matched, warning), но матчится на уровне `/slide[N]/shape[@id=X]/paragraph[1]`.
- Если нужно перезаписать сложный шейп — надёжнее `set` по `paragraph[1]` с новым текстом, чем искать точную строку.

## Атомарность батчей
- По умолчанию батч атомарен: один фейл → откат всего (в JSON `atomicRolledBack: true`). Для смесей рискованных операций `--best-effort`, но тогда проверять каждую операцию в ответе.
- `--json` обязателен: без него не видно, что именно сфейлилось.

## QA-гейты, которые реально ловят мусор
- `validate` + `view issues`: ловят переполнение текста (с `suggest.height` — применять батчем одним заходом) и low-contrast (#97A3AC на тёмных карточках → F2F5F7). Гнать до 0 issues.
- `view screenshot` требует headless browser — в окружении его нет. Фолбэк: `officecli view file html -o preview.html`, затем
  `google-chrome --headless=new --no-sandbox --screenshot=deck.png --window-size=1600,10000 file:///…/preview.html`
  → весь дек одним PNG → `vision_analyze`. Пер-слайд: pptx-html рендерится одним документом (скролл), hash-навигации нет — либо кроп PNG, либо `--print-to-pdf` и проверка страниц.
- Цикл: правки → `view issues` → render → vision; на живом деке сходится за ~3 круга. Каждый следующий круг находит меньше — когда два круга «0 issues», стоп.

## Жизненный цикл
- `open` в начале работы, `save`/`close` перед сторонними читателями (chrome, python).
- Пустые заметки (`notes`) на контентных слайдах — обязательны, добавлять последним штрихом на слайд.
- Диалоговые чат-карточки на тёмном: bubble q = surface, bubble a = accent-soft на темной карточке + белый текст.

## Когда вообще не стоит
- Клиентская презентация на встречу: юзеру зашёл HTML-дек, pptx-дизайн отверг («кровь из глаз»). Сначала убедиться, что формат действительно .pptx (skill `html-slide-decks`).
